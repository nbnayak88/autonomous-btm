TOGAF Phases E and F and the 9P4V Venture pillar: reuse the blueprint for the audits an organisation already runs.

Why extend

The P2P design is a blueprint, not a one-off. About four-fifths of it does not depend on the process: secure extract, masking, staging, the event-log pattern, the control-test library, deviation workflow, evidence and the AI use rule. What changes per audit is the source data, the event model and the control tests.

How to read "Signavio fit". Strong: the domain is a transactional process with clear events, and templated content exists or the build mirrors P2P. Partial: the flow can be mined but the event log is built by hand, or the data is partly outside SAP. Limited: the process view helps, but the core test is a data check best done outside the mining tool. This is a design judgement from public product information; validate each domain with the vendor before committing.

Recommended order (waves)

  1. Wave 1: P2P and master data. The change-log extract is shared.
  2. Wave 2: revenue, supply chain, IT service and access, finance close. All are transactional with strong event data.
  3. Wave 3: HR and CX. Add privacy review and a custom event log.
  4. Wave 4: ESG. Start with the process of data capture and approval, then decide on analytics outside the tool.

Finance audit (record-to-report)

Journal entries, period close and reconciliations.

What differs from P2P. Fewer linked objects than P2P; the main risks are who posts, when and to which account. Close tasks are timed activities and suit KPI views.

HR audit (hire-to-retire)

Hiring, pay changes, time and exits.

What differs from P2P. There is no standard event template assumed here, so the log is built from change history. Personal data is heavier: pseudonymise before load, restrict roles, and involve the data protection lead before the first extract.

ESG audit

Capture, approval and reporting of sustainability metrics.

What differs from P2P. The metric itself (for example an emissions total) is a calculation, not a process. Use process intelligence for the path the data took: who entered it, who changed it, who approved it, and whether it was on time.

Decisions for the extension

  • Shared test library. One library, one owner, tests grouped by domain. Do not copy the library per audit.
  • One event model per domain, one shared master-data model. Avoid a single giant model.
  • Privacy first for HR and CX. Gate the build on a masking review.
  • Licence and capacity. Event volume grows with each domain; size and confirm with the vendor before wave 2.
  • Status of AI features is unchanged: assistive only, beta and roadmap features stay out of the critical path.

Open questions

  • Which domain has the strongest audit demand this year?
  • Where does the data live today, and who owns it?
  • Which tests already exist as spreadsheets and can move into the library first?
